# v3.0 Python Removal Plan — Inventory, hub-api Fold-In, Waves, Cutover

**Status:** Approved direction (Justin) — this doc is the execution plan, not a design-from-scratch.
**Date:** 2026-09-28
**Scope:** Every Python component outside `hub_api/` in this monorepo (`core/`, `services/`, `action/`, `trigger/`, `processing/`).
**Mandate (Justin, verbatim intent):**
(a) Platform connectors → WASM connector bundles in svc-ingest/svc-action — designed separately on branch `docs/connector-bundles-design` (currently an empty foundation branch off `release/v3.0.X`; this plan references it, does not duplicate it).
(b) Everything below lands in v3.0 — no deferral to v3.1.
(c) `core-community`, `core-data`, `core-identity` fold into `hub_api`.
(d) Business-logic modules in `svc_process`/`svc_action`/interactive-\* become **app bundles** — Python bundles are fine, because they run as guest code *inside* the Rust executor (svc-\*-rust host), not as a freestanding Python service handling live traffic directly.
(e) **New (mid-plan correction from Justin):** every data-plane → hub-api call becomes internal gRPC (`waddles.hub.internal.v1`, foundation on branch `feature/hub-api-internal-grpc`) — REST is for webui + external API only.

**Related, already in flight (do not re-litigate, reference only):**
- PR #441 `chore/retire-python-dataplane` — Rust parity gap list for svc-ingest/process/action (OPEN, audit-only, no removal yet).
- PR #415 `docs/bundle-db-capability-design` (MERGED) — bundle `db` capability + `app_core`/`app_community` schema design.
- Issue #425 — `kv` bundle host capability (OPEN).
- Issue #428 — `bundle_capability_gate` crate (OPEN).
- Issue #433 — wire `capability_gate::authorize()` into svc_process/svc_action (OPEN).
- Issue #419 — `bundle_capability_gate` permission catalog design (OPEN) — target for the new `streaming.lifecycle.subscribe`/`overlay.media` permission ids (§3).
- Issue #456 — svc-streaming-rust core service + stream-lifecycle bundle extension (OPEN).
- Issue #457 — svc-presentation-rust core service + `overlay.media` bundle extension (OPEN).
- `docs/APP_BUNDLE_AUTHORING.md` (FROZEN) — the bundle entrypoint contract every Wave-3 bundle must match exactly.
- `hub_api/PORTING.md` — the Node→Quart hub-api porting recipe M1..M9 already established; **the (c) fold-in extends this same recipe**, it does not invent a new one.

## 0. Key findings that reshape the mandate's literal reading

1. **The 16 svc_process bundles and 18 svc_action bundles already exist and are already bundle-shaped** (`core/svc_process/bundles/*.py`, `core/svc_action/bundles/*.py`, conform to the frozen `normalize`/`transform`/action entrypoint contract). PR #441's "0% business-logic parity" verdict is about the **Rust WASM engine having no compiled bundles**, not about these Python files needing a rewrite. Per Justin's clarification (d), they don't need a Rust rewrite — they need the Rust host (`svc-process-rust`/`svc-action-rust`) to gain a Python-bundle-execution capability. **This is the single biggest scope reduction in the plan** — Wave 3 is "finish the 9 missing bundles + wire Rust-hosted execution," not "port 34 bundles to Rust."
2. **Much of the (c) hub-api fold-in is already done or half-done** via the parallel Node→Quart hub-api port (`hub_api/PORTING.md` M1–M9). `hub_api/services/schema.py` already defines `community_polls`/`poll_options`/`poll_votes` and `community_forms`/`form_fields`/`form_submissions`/`form_field_values` — **byte-identical table names to `core/engagement_module/app.py`** (core-data). `hub_api/blueprints/v1/` already has `community_polls.py`, `community_forms.py`, `community_reputation.py`, `identity.py`, `workflow.py`, `community_loyalty.py`, `music.py`, `stream.py`. **Confirmed collision, not confirmed duplication of effort** — a parity audit (Wave 1) must run before any new fold-in code is written, or two independent implementations of the same tables get built in parallel.
3. **`labels`/`entity_labels` (labels_core_module) have no hub-api equivalent** — genuine, uncontested gap.
4. **9 of the 18 `action/interactive/*` legacy modules are already superseded** by existing svc_process/svc_action bundles (name/feature match): `alias_interaction_module`→`social_alias_{process,action}`, `quote_interaction_module`→`social_quote_{process,action}`, `shoutout_interaction_module`→`social_shoutout_process`+`twitch_shoutout_action`, `welcome_interaction_module`→`social_welcome_{process,action}`, `spotify_interaction_module`+`youtube_music_interaction_module`→`social_music_{process,action}`, `loyalty_interaction_module`→`community_loyalty_{process,action}`, `inventory_interaction_module`→`inventory_process`. The other **9 have no bundle yet**: `ai_interaction_module`, `calendar_interaction_module`, `clip_interaction_module`, `lfg_interaction_module`, `memories_interaction_module`, `presence_module`, `server_manager_interaction_module`, `server_status_interaction_module`, `translate_interaction_module`. (Name-match mapping — Wave 1d re-confirms before any deletion.)
5. All legacy `core/*_module` Quart services already point at the **same physical Postgres** hub-api uses (`init_database(Config.DATABASE_URL)`), so most of (c) is a process/API-surface consolidation, not a data migration. Only the modules that `define_table()` locally (`engagement_module`, `labels_core_module`; `security_core_module` only references, doesn't define) carry real schema-ownership questions.
6. **Resolved (Justin):** `core/svc_streaming` and `core/svc_presentation` are Rust core services, not hub-api fold-ins and not accepted Python exceptions — "Streaming and overlay should be rust and considered core. However they should allow for app bundle deployments for extension." Both keep/gain bundle **extension points** (stream lifecycle hooks; `overlay.media` capability) rather than staying closed Rust monoliths — see §3.

## 3. Rust Core Services with Bundle Extension Points (svc-streaming-rust, svc-presentation-rust)

**Resolved by Justin** (supersedes the original two Open Questions on this doc): *"Streaming and overlay should be rust and considered core. However they should allow for app bundle deployments for extension."* Tracked as their own issues: #456 (svc-streaming-rust), #457 (svc-presentation-rust).

### 3.1 svc-streaming-rust

- Replaces `core/svc_streaming`'s Python control-plane + Python-orchestrated `ffmpeg` subprocess with a Rust core service. `ffmpeg`/`gstreamer` stay as the actual media engine — driven from Rust (process supervision, pipeline control), not rewritten.
- Owns `stream_configs`/`stream_status`/`stream_destinations` — resolves the three-way collision flagged in §2.1 (`video_proxy_module`, hub-api's `stream.py`/`streaming.py`, and `svc_streaming`'s own schema previously all touched stream config). hub-api may keep a thin webui read-through; writes + the actual relay live here.
- **Bundle extension points:** stream lifecycle hooks — `on-start`, `on-stop`, `on-segment`, `on-recording-ready` — invoke app bundles through a new or extended WIT world (extends the `stage.wit` family, see `docs/superpowers/specs/2026-09-28-wit-stage-v1-1-design.md`). New permission ids added to the `bundle_capability_gate` catalog (issue #419) for this world, e.g. `streaming.lifecycle.subscribe`, `AppScoped` per community/stream.
- Dependencies: issue #419 (permission catalog), issue #428 (`bundle_capability_gate` crate).

### 3.2 svc-presentation-rust

- Replaces `core/svc_presentation`'s Python SSE/websocket overlay push with a Rust core service (Axum, SSE/websocket).
- Performs server-side detokenization (PII boundary: overlays receive only detokenized display-safe fields via an egress detokenization call to hub-api, never raw PII) and server-side HTML escaping for every overlay render path.
- Owns `overlay_surfaces`/`presentation_config` and absorbs `browser_source_core_module`'s `/overlay/*` routes + `/ws/captions/<community_id>` websocket (§2.1) — this does **not** fold into hub-api.
- **Bundle extension points:** a new `overlay.media` host capability lets bundles push overlay widgets/media (permission id added to the `bundle_capability_gate` catalog, issue #419, egress-detokenization-scoped); bundles may also register overlay renderers/widget templates in a sandboxed form — rendered inside an iframe with a locked-down `sandbox` attribute and a strict CSP, so no bundle-supplied script runs with overlay-host privileges.
- Dependencies: issue #419 (permission catalog + `overlay.media`), issue #428 (`bundle_capability_gate`), egress detokenization chain.

## 4. Internal gRPC Migration — `waddles.hub.internal.v1`

**Constraint (Justin):** every data-plane → hub-api call (including the core-community/core-data/core-identity functionality now living in hub-api) is internal gRPC. REST stays for webui + external API. Foundation branch `feature/hub-api-internal-grpc` exists off `release/v3.0.X` (currently an empty scaffold — no code yet).

**Current REST call sites (confirmed by grep):** `core/svc_ingest/app.py`, `core/svc_process/app.py` + `runner.py`, `core/svc_action/app.py` + `runner.py`, `core/svc_action/config.py` — all use `httpx` against hub-api's `blueprints/v1/distribution.py` (bundle-activation polling) and dispatch/audit-log endpoints. `core/svc_process/services/reputation_gate_client.py` is a second, separate REST client — confirm at Wave 1f whether it targets hub-api or a different service.

**Per backend.md:** gRPC is already the mandatory service-to-service transport; this migration closes the gap where svc-ingest/process/action took the REST fallback instead. Two proto layers per `backend.md` API Versioning: `waddles.hub.internal.v1` package + `api_version` field in every request message.

| Task | Detail |
|---|---|
| 5a. Proto definitions | `waddles.hub.internal.v1`: distribution/bundle-poll service, activity/audit dispatch-log service, reputation-read service (for #428's `ReputationScoped`), any community/identity read the data plane needs post-fold-in |
| 5b. hub-api gRPC server | `grpc.aio` server alongside the existing Quart/hypercorn app (separate port), SPIFFE-ready mTLS + short-lived signed JWT per call (`security.md` Service-to-Service Auth) — no shared secrets |
| 5c-5e. Client migration | Swap `httpx` for generated `waddles.hub.internal.v1` stubs in svc-ingest, svc-process (+runner), svc-action (+runner, +reputation_gate_client) |
| 5f. Rust-native clients | Build `tonic` gRPC clients directly into svc-ingest-rust/svc-process-rust/svc-action-rust — never write a second REST client for the Rust hosts |
| 5g. REST surface cleanup | Once 5c-5f land, either remove the now-internal-only REST endpoints from the public v1 surface or gate them behind an internal-only flag if webui still needs a subset |

## 6. Per-Component Cutover & Decommission Checklist

Apply this template to every row in §1 marked HUB, FB, CB, or DEL:

```
[ ] 1. Parity test: new destination reproduces every legacy endpoint/bundle-stage/behavior
       (fail-first test per hub_api/PORTING.md step 6, or bundle contract test per
       docs/APP_BUNDLE_AUTHORING.md) — written BEFORE traffic switches.
[ ] 2. Feature-flag the new path (PostHog, default OFF) if user-visible behavior changes.
[ ] 3. Traffic switch: activate new destination for a subset (single tenant/community in
       alpha), verify OTel logs+metrics+traces emit correctly (critical-rules.md Observability).
[ ] 4. Full traffic cutover; old path left running but unreferenced for one release cycle
       (rollback window).
[ ] 5. Python deployment removed: Helm Deployment/Service/NetworkPolicy/HPA deleted for the
       retired service — helm lint/template confirms no dangling references.
[ ] 6. Code deleted: source tree removed, requirements.txt/pyproject.toml pruned, CI workflow
       steps for that service removed.
[ ] 7. Regression test added if this component was ever the subject of a GitHub issue
       (testing.md GitHub issue regression rule).
```

**Worked example — `labels_core_module` → hub-api (§2.2):** (1) `tests/test_v1_labels_blueprint.py` asserting `labels`/`entity_labels` CRUD parity with the legacy module's `app.py` behavior → (2) `waddles.labels-in-hub` flag OFF → (3) flip for one alpha tenant, confirm OTel → (4) full cutover, `services/core-data` still deployed but `labels_core_module` import path unused → (5) after one release, remove `labels_core_module`'s slice from `services/core-data`'s Helm values (or the whole chart once 2a-2c all land) → (6) delete `core/labels_core_module/`, drop from `services/core-data/requirements.in` → (7) n/a unless a filed issue named it.
